1. OSS とライセンス ★★★

OSS（オープンソースソフトウェア）

  • ソースコードが公開され、利用・改変・再配布が認められたソフトウェア
  • 定義は OSI（Open Source Initiative）の OSD（The Open Source Definition）。「再配布の自由」「ソースコードの入手」「派生物の許可」「個人・団体・利用分野で差別しない」など10項目
  • ⚠ 「無償」は OSS の条件ではない。有償で販売・サポートしてもよい

主なライセンスの分類

種類 代表例 改変物を配布するときの義務
コピーレフト型 GPL 派生物にも GPL を適用し、ソースコードを公開する
弱いコピーレフト型 LGPL、MPL ライブラリ自体を改変したら公開。リンクして使うだけなら自作部分は公開不要
非コピーレフト型（寛容型） BSD、MIT、Apache、PostgreSQL ライセンス 著作権表示と免責条項を残せばよい。ソース公開義務なし

PostgreSQL ライセンス

  • BSD / MIT ライセンスに近い寛容型のライセンス
  • 商用利用・改変・再配布が自由。改変したソースコードを公開する義務はない
  • 条件は「著作権表示・ライセンス文・免責条項を残す」ことだけ
  • 無償で利用できる。PostgreSQL を組み込んだ製品を、ソース非公開で販売してもよい
  • ⚠ PostgreSQL は GPL ではない。MySQL（GPL と商用ライセンスのデュアルライセンス）と混同しない

2. PostgreSQL の歴史と開発体制 ★★

歴史

年 出来事
1986 カリフォルニア大学バークレー校で POSTGRES プロジェクト開始（Michael Stonebraker 教授）。Ingres の後継研究
1994 Postgres95。問い合わせ言語を PostQUEL から SQL に置き換え、psql を追加
1996 PostgreSQL に改名。最初のバージョンは 6.0

開発体制

  • 特定の企業が所有・開発しているのではなく、PostgreSQL Global Development Group（世界中の開発者のコミュニティ）が開発
  • 誰でも参加できる。開発の議論・パッチ投稿はメーリングリスト（開発者向けの pgsql-hackers など）で行い、パッチは CommitFest（定期的なレビュー期間）で審査される
  • 日本には 日本 PostgreSQL ユーザ会（JPUG） があり、勉強会・ドキュメント翻訳などを行う

バグ報告

  • 公式サイトのバグ報告フォーム、または pgsql-bugs メーリングリストで報告する
  • 報告には PostgreSQL のバージョン（SELECT version(); で確認）、OS、再現手順、期待した結果と実際の結果を書く

3. バージョンとリリースサイクル ★★★

バージョン番号の付け方

メジャーバージョン マイナーバージョン
10 以降 1つ目の数字（10 → 11 → 12） 2つ目の数字（14.0 → 14.1）
9.6 以前 1つ目と2つ目の数字（9.5 → 9.6） 3つ目の数字（9.6.1 → 9.6.2）
  • ⚠ 「14.5」はメジャー14のマイナー5。「9.6.5」はメジャー9.6のマイナー5

リリースとサポート

  • メジャーバージョン: 年1回（例年 9〜10月）リリース。新機能が入る
  • マイナーバージョン: 少なくとも3か月に1回リリース。バグ修正・セキュリティ修正のみ（新機能は入らない）。重大な脆弱性はスケジュール外でも出る
  • サポート期間: 各メジャーバージョンは初回リリースから 5年間。期限後に最終マイナーリリースを出して EOL（サポート終了）
  • コミュニティは最新のマイナーバージョンを使うことを推奨している

アップグレード方法

  • マイナーアップグレード: サーバを停止 → プログラム（バイナリ）を入れ替え → 再起動。データベースクラスタはそのまま使える（ダンプ・リストア不要）
  • メジャーアップグレード: データディレクトリの形式に互換性がないため、次のどちらかが必要
    • pg_dump / pg_dumpall でダンプ → 新バージョンでリストア
    • pg_upgrade で変換
  • ⚠ メジャーバージョンは途中を飛ばして（例: 12 → 16）アップグレードしてよい

4. PostgreSQL の主な機能・特徴 ★★

  • ACID 特性を満たすトランザクション
  • MVCC（多版型同時実行制御）: 更新時に行の新しい版を作り、古い版を残す → 読み取りと書き込みが互いをブロックしない。不要になった古い行は VACUUM で回収する
  • WAL（先行書き込みログ）: 変更をデータファイルより先にログへ書く → クラッシュ時の復旧、PITR（ポイントインタイムリカバリ）、レプリケーションの基盤
  • SQL 標準への高い準拠
  • 拡張性: ユーザー定義のデータ型・関数・演算子・インデックス方式を追加できる。CREATE EXTENSION で拡張機能を導入
  • 手続き言語: PL/pgSQL（標準）、PL/Perl、PL/Python、PL/Tcl
  • 豊富なデータ型: JSON / JSONB、配列、範囲型、幾何データ型、ネットワークアドレス型 など
  • インデックス方式: B-tree（デフォルト）、Hash、GiST、SP-GiST、GIN、BRIN
  • レプリケーション: ストリーミングレプリケーション（物理）、論理レプリケーション（CREATE PUBLICATION / CREATE SUBSCRIPTION）
  • 宣言的パーティショニング（PARTITION BY / PARTITION OF）、パラレルクエリ
  • マルチプロセス構成: 接続ごとにサーバプロセス（バックエンド）が1つ起動する（スレッドではない）
  • 対応 OS: Linux・Windows・macOS・各種 UNIX

5. リレーショナルデータモデルの基本 ★★

  • 1970年に E.F. Codd が提唱。データを表（リレーション）で表し、集合演算で操作する

用語の対応

リレーショナルモデル SQL / 一般的な呼び方
リレーション テーブル（表）
タプル 行（レコード）
属性 列（カラム）
定義域（ドメイン） 列が取りうる値の集合（データ型＋制約）
次数 列の数
濃度（カーディナリティ） 行の数

キー

  • スーパーキー: 行を一意に識別できる属性の組（余分な属性を含んでもよい）
  • 候補キー: 行を一意に識別できる最小の属性の組
  • 主キー（PRIMARY KEY）: 候補キーから1つ選んだもの。一意（UNIQUE）かつ NOT NULL。1テーブルに1つだけ
  • 代替キー: 主キーに選ばれなかった候補キー
  • 複合キー: 複数の列からなるキー
  • 外部キー（FOREIGN KEY）: 他のテーブルの主キー（または UNIQUE 列）を参照する列。参照整合性（存在しない値を参照させない）を保証する
  • ⚠ 外部キーの列には NULL を入れてよい（参照先が無い状態を表す）

NULL

  • 「値が不明」「値が存在しない」ことを表す特別なマーカー。0 や空文字（’‘）とは別物
  • NULL との比較（= NULL、<> NULL）の結果は真でも偽でもない UNKNOWN（NULL）→ 判定には IS NULL / IS NOT NULL を使う

関係演算

演算 内容 SQL での表現
選択（制限） 条件に合う行を取り出す WHERE
射影 特定の列を取り出す SELECT 列名
結合 共通の列で2つの表をつなぐ JOIN
和 両方の行を合わせる UNION
差 一方にだけある行 EXCEPT
積（共通） 両方にある行 INTERSECT
直積 すべての行の組み合わせ CROSS JOIN
商 割り算に相当する演算 直接の構文なし
  • ⚠ 「選択 = 行」「射影 = 列」を逆にした選択肢が定番の引っ掛け

6. データベース管理システム（DBMS）の役割 ★

  • データ定義: 表・制約などの構造を定義する
  • データ操作: 検索・追加・更新・削除
  • 整合性の維持: 制約（主キー・外部キー・CHECK など）で不正なデータを防ぐ
  • 同時実行制御: 複数ユーザーが同時に使っても矛盾しない（ロック・MVCC）
  • 障害回復: ログ（WAL）を使ってクラッシュ前の確定済みの状態へ戻す
  • セキュリティ: ユーザー認証とアクセス権限の管理
  • データ独立性: 物理的な格納方法を変えてもアプリケーションに影響しない（3層スキーマ: 外部スキーマ / 概念スキーマ / 内部スキーマ）

ACID 特性

特性 意味
Atomicity（原子性） トランザクションは全部実行されるか、全く実行されないかのどちらか
Consistency（一貫性） トランザクションの前後でデータが制約を満たした正しい状態に保たれる
Isolation（独立性・分離性） 同時に実行されるトランザクションが互いに影響しない
Durability（永続性） コミットした結果は障害が起きても失われない

7. SQL の一般知識と分類 ★★★

SQL の特徴

  • リレーショナルデータベースを操作する標準言語（ISO / JIS で規格化）
  • 宣言型の言語: 「どうやって取り出すか」ではなく「何が欲しいか」を書く
  • キーワード（SELECT など）は大文字・小文字を区別しない
  • 引用符で囲まない識別子（テーブル名・列名）は、PostgreSQL では小文字に変換される。大文字を区別したいときは二重引用符（"MyTable"）で囲む
  • 文字列リテラルは単一引用符（'abc'）で囲む
  • コメントは --（行末まで）と /* */（範囲）
  • 文の終わりは ;

SQL の分類

分類 正式名 主なコマンド
DDL Data Definition Language（データ定義言語） CREATE、ALTER、DROP（TRUNCATE も DDL に分類されることが多い）
DML Data Manipulation Language（データ操作言語） SELECT、INSERT、UPDATE、DELETE
DCL Data Control Language（データ制御言語） GRANT、REVOKE。トランザクション制御（BEGIN、COMMIT、ROLLBACK）も DCL に含めることが多い
  • ⚠ GRANT / REVOKE は DCL（DDL ではない）
  • ⚠ SELECT は DML（「データを変更しないから DML ではない」は誤り）

8. データベース設計と正規化 ★★★

設計の流れ

  1. 概念設計: 業務の対象を E-R 図で表す（DBMS に依存しない）
  2. 論理設計: テーブル・列・キーを決め、正規化する
  3. 物理設計: インデックス・格納場所など、特定の DBMS に合わせて決める

E-R 図

  • エンティティ（実体: 顧客・商品など）、属性、リレーションシップ（関連）で表す
  • 関連の多重度: 1対1、1対多、多対多
  • ⚠ 多対多の関連はそのままテーブルにできない → 連関エンティティ（中間テーブル）を作って1対多の2つに分解する

関数従属

  • 関数従属: 列 A の値が決まると列 B の値が1つに決まる（A → B）
  • 部分関数従属: 複合キーの一部だけで、非キー列が決まる
  • 推移関数従属: キー → 非キー列 X → 非キー列 Y のように、非キー列を経由して決まる

正規形

正規形 条件 やること
第1正規形 すべての列が単一の値（原子値）を持つ。繰り返し項目がない 繰り返し項目を別の行・別の表に分ける
第2正規形 第1正規形 ＋ 部分関数従属がない 複合キーの一部で決まる列を別表に分ける
第3正規形 第2正規形 ＋ 推移関数従属がない 非キー列で決まる列を別表に分ける
  • ⚠ 主キーが単一の列なら、第1正規形の時点で部分関数従属は起こらない（自動的に第2正規形）

例: 受注表の正規化

非正規形: 受注(受注番号, 受注日, 顧客番号, 顧客名, {商品番号, 商品名, 数量}) ※ { } は繰り返し

  • 第1正規形: 繰り返しをなくす → 受注明細(受注番号, 商品番号, 受注日, 顧客番号, 顧客名, 商品名, 数量)（主キー: 受注番号＋商品番号）
  • 第2正規形: 部分関数従属をなくす
    • 受注(受注番号, 受注日, 顧客番号, 顧客名) ← 受注番号だけで決まる
    • 商品(商品番号, 商品名) ← 商品番号だけで決まる
    • 受注明細(受注番号, 商品番号, 数量)
  • 第3正規形: 推移関数従属（受注番号 → 顧客番号 → 顧客名）をなくす
    • 受注(受注番号, 受注日, 顧客番号)
    • 顧客(顧客番号, 顧客名)

正規化の目的

  • データの重複（冗長性）をなくす
  • 更新時異常を防ぐ: 挿入時異常（商品を登録したいのに受注が無いと登録できない）、更新時異常（顧客名を一部の行だけ直して矛盾する）、削除時異常（最後の受注を消すと顧客情報まで消える）
  • ⚠ 正規化を進めると結合（JOIN）が増えて検索が遅くなることがある。性能のために意図的に正規化を崩すことを非正規化という
