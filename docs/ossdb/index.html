1. OSS とライセンス ★★★

OSS（オープンソースソフトウェア）

  • ソースコードが公開され、利用・改変・再配布が認められたソフトウェア
  • 定義は OSI（Open Source Initiative）の OSD（The Open Source Definition）。「再配布の自由」「ソースコードの入手」「派生物の許可」「個人・団体・利用分野で差別しない」など10項目
  • ⚠ 「無償」は OSS の条件ではない。有償で販売・サポートしてもよい

主なライセンスの分類

種類 代表例 改変物を配布するときの義務
コピーレフト型 GPL 派生物にも GPL を適用し、ソースコードを公開する
弱いコピーレフト型 LGPL、MPL ライブラリ自体を改変したら公開。リンクして使うだけなら自作部分は公開不要
非コピーレフト型（寛容型） BSD、MIT、Apache、PostgreSQL ライセンス 著作権表示と免責条項を残せばよい。ソース公開義務なし

PostgreSQL ライセンス

  • BSD / MIT ライセンスに近い寛容型のライセンス
  • 商用利用・改変・再配布が自由。改変したソースコードを公開する義務はない
  • 条件は「著作権表示・ライセンス文・免責条項を残す」ことだけ
  • 無償で利用できる。PostgreSQL を組み込んだ製品を、ソース非公開で販売してもよい
  • ⚠ PostgreSQL は GPL ではない。MySQL（GPL と商用ライセンスのデュアルライセンス）と混同しない

4. PostgreSQL の主な機能・特徴 ★★

  • ACID 特性を満たすトランザクション
  • MVCC（多版型同時実行制御）: 更新時に行の新しい版を作り、古い版を残す → 読み取りと書き込みが互いをブロックしない。不要になった古い行は VACUUM で回収する
  • WAL（先行書き込みログ）: 変更をデータファイルより先にログへ書く → クラッシュ時の復旧、PITR（ポイントインタイムリカバリ）、レプリケーションの基盤
  • SQL 標準への高い準拠
  • 拡張性: ユーザー定義のデータ型・関数・演算子・インデックス方式を追加できる。CREATE EXTENSION で拡張機能を導入
  • 手続き言語: PL/pgSQL（標準）、PL/Perl、PL/Python、PL/Tcl
  • 豊富なデータ型: JSON / JSONB、配列、範囲型、幾何データ型、ネットワークアドレス型 など
  • インデックス方式: B-tree（デフォルト）、Hash、GiST、SP-GiST、GIN、BRIN
  • レプリケーション: ストリーミングレプリケーション（物理）、論理レプリケーション（CREATE PUBLICATION / CREATE SUBSCRIPTION）
  • 宣言的パーティショニング（PARTITION BY / PARTITION OF）、パラレルクエリ
  • マルチプロセス構成: 接続ごとにサーバプロセス（バックエンド）が1つ起動する（スレッドではない）
  • 対応 OS: Linux・Windows・macOS・各種 UNIX

5. リレーショナルデータモデルの基本 ★★

  • 1970年に E.F. Codd が提唱。データを表（リレーション）で表し、集合演算で操作する

用語の対応

リレーショナルモデル SQL / 一般的な呼び方
リレーション テーブル（表）
タプル 行（レコード）
属性 列（カラム）
定義域（ドメイン） 列が取りうる値の集合（データ型＋制約）
次数 列の数
濃度（カーディナリティ） 行の数

キー

  • スーパーキー: 行を一意に識別できる属性の組（余分な属性を含んでもよい）
  • 候補キー: 行を一意に識別できる最小の属性の組
  • 主キー（PRIMARY KEY）: 候補キーから1つ選んだもの。一意（UNIQUE）かつ NOT NULL。1テーブルに1つだけ
  • 代替キー: 主キーに選ばれなかった候補キー
  • 複合キー: 複数の列からなるキー
  • 外部キー（FOREIGN KEY）: 他のテーブルの主キー（または UNIQUE 列）を参照する列。参照整合性（存在しない値を参照させない）を保証する
  • ⚠ 外部キーの列には NULL を入れてよい（参照先が無い状態を表す）

NULL

  • 「値が不明」「値が存在しない」ことを表す特別なマーカー。0 や空文字（''）とは別物
  • NULL との比較（= NULL、<> NULL）の結果は真でも偽でもない UNKNOWN（NULL）→ 判定には IS NULL / IS NOT NULL を使う

関係演算

演算 内容 SQL での表現
選択（制限） 条件に合う行を取り出す WHERE
射影 特定の列を取り出す SELECT 列名
結合 共通の列で2つの表をつなぐ JOIN
和 両方の行を合わせる UNION
差 一方にだけある行 EXCEPT
積（共通） 両方にある行 INTERSECT
直積 すべての行の組み合わせ CROSS JOIN
商 割り算に相当する演算 直接の構文なし
  • ⚠ 「選択 = 行」「射影 = 列」を逆にした選択肢が定番の引っ掛け

6. データベース管理システム（DBMS）の役割 ★

  • データ定義: 表・制約などの構造を定義する
  • データ操作: 検索・追加・更新・削除
  • 整合性の維持: 制約（主キー・外部キー・CHECK など）で不正なデータを防ぐ
  • 同時実行制御: 複数ユーザーが同時に使っても矛盾しない（ロック・MVCC）
  • 障害回復: ログ（WAL）を使ってクラッシュ前の確定済みの状態へ戻す
  • セキュリティ: ユーザー認証とアクセス権限の管理
  • データ独立性: 物理的な格納方法を変えてもアプリケーションに影響しない（3層スキーマ: 外部スキーマ / 概念スキーマ / 内部スキーマ）

ACID 特性

特性 意味
Atomicity（原子性） トランザクションは全部実行されるか、全く実行されないかのどちらか
Consistency（一貫性） トランザクションの前後でデータが制約を満たした正しい状態に保たれる
Isolation（独立性・分離性） 同時に実行されるトランザクションが互いに影響しない
Durability（永続性） コミットした結果は障害が起きても失われない

7. SQL の一般知識と分類 ★★★

SQL の特徴

  • リレーショナルデータベースを操作する標準言語（ISO / JIS で規格化）
  • 宣言型の言語: 「どうやって取り出すか」ではなく「何が欲しいか」を書く
  • キーワード（SELECT など）は大文字・小文字を区別しない
  • 引用符で囲まない識別子（テーブル名・列名）は、PostgreSQL では小文字に変換される。大文字を区別したいときは二重引用符（"MyTable"）で囲む
  • 文字列リテラルは単一引用符（'abc'）で囲む
  • コメントは --（行末まで）と /* */（範囲）
  • 文の終わりは ;

SQL の分類

分類 正式名 主なコマンド
DDL Data Definition Language（データ定義言語） CREATE、ALTER、DROP（TRUNCATE も DDL に分類されることが多い）
DML Data Manipulation Language（データ操作言語） SELECT、INSERT、UPDATE、DELETE
DCL Data Control Language（データ制御言語） GRANT、REVOKE。トランザクション制御（BEGIN、COMMIT、ROLLBACK）も DCL に含めることが多い
  • ⚠ GRANT / REVOKE は DCL（DDL ではない）
  • ⚠ SELECT は DML（「データを変更しないから DML ではない」は誤り）

8. データベース設計と正規化 ★★★

設計の流れ

  1. 概念設計: 業務の対象を E-R 図で表す（DBMS に依存しない）
  2. 論理設計: テーブル・列・キーを決め、正規化する
  3. 物理設計: インデックス・格納場所など、特定の DBMS に合わせて決める

E-R 図

  • エンティティ（実体: 顧客・商品など）、属性、リレーションシップ（関連）で表す
  • 関連の多重度: 1対1、1対多、多対多
  • ⚠ 多対多の関連はそのままテーブルにできない → 連関エンティティ（中間テーブル）を作って1対多の2つに分解する

関数従属

  • 関数従属: 列 A の値が決まると列 B の値が1つに決まる（A → B）
  • 部分関数従属: 複合キーの一部だけで、非キー列が決まる
  • 推移関数従属: キー → 非キー列 X → 非キー列 Y のように、非キー列を経由して決まる

正規形

正規形 条件 やること
第1正規形 すべての列が単一の値（原子値）を持つ。繰り返し項目がない 繰り返し項目を別の行・別の表に分ける
第2正規形 第1正規形 ＋ 部分関数従属がない 複合キーの一部で決まる列を別表に分ける
第3正規形 第2正規形 ＋ 推移関数従属がない 非キー列で決まる列を別表に分ける
  • ⚠ 主キーが単一の列なら、第1正規形の時点で部分関数従属は起こらない（自動的に第2正規形）

例: 受注表の正規化

非正規形: 受注(受注番号, 受注日, 顧客番号, 顧客名, {商品番号, 商品名, 数量}) ※ { } は繰り返し

  • 第1正規形: 繰り返しをなくす → 受注明細(受注番号, 商品番号, 受注日, 顧客番号, 顧客名, 商品名, 数量)（主キー: 受注番号＋商品番号）
  • 第2正規形: 部分関数従属をなくす
    • 受注(受注番号, 受注日, 顧客番号, 顧客名) ← 受注番号だけで決まる
    • 商品(商品番号, 商品名) ← 商品番号だけで決まる
    • 受注明細(受注番号, 商品番号, 数量)
  • 第3正規形: 推移関数従属（受注番号 → 顧客番号 → 顧客名）をなくす
    • 受注(受注番号, 受注日, 顧客番号)
    • 顧客(顧客番号, 顧客名)

正規化の目的

  • データの重複（冗長性）をなくす
  • 更新時異常を防ぐ: 挿入時異常（商品を登録したいのに受注が無いと登録できない）、更新時異常（顧客名を一部の行だけ直して矛盾する）、削除時異常（最後の受注を消すと顧客情報まで消える）
  • ⚠ 正規化を進めると結合（JOIN）が増えて検索が遅くなることがある。性能のために意図的に正規化を崩すことを非正規化という

1. データ型 ★★★

数値型

型 サイズ 範囲・特徴
smallint（int2） 2バイト -32768 〜 32767
integer（int / int4） 4バイト 約 ±21億。整数の標準
bigint（int8） 8バイト 約 ±922京
numeric(p, s)（decimal） 可変 精度 p（全体の桁数）・位取り s（小数点以下の桁数）を指定する正確な数値。金額向き
real（float4） 4バイト 単精度浮動小数点（有効桁 約6桁）。誤差がある
double precision（float8） 8バイト 倍精度浮動小数点（有効桁 約15桁）。誤差がある
smallserial / serial / bigserial 2 / 4 / 8バイト 自動採番（実体は整数型＋シーケンス。→ 03章）
  • numeric(5, 2) は全体5桁・小数2桁 → 最大 999.99
    • 小数部が s を超える値（123.456）は丸められて入る（123.46）
    • 整数部が収まらない値（1234.5）は エラー（numeric field overflow）
  • numeric を精度なしで書くと、上限内で任意の桁数を持てる
  • integer 列に 1.5 を入れると四捨五入されて 2 になる（エラーではない）

文字列型

型 特徴
char(n)（character） 固定長。n 文字に満たない分は空白で埋める。char だけなら char(1)
varchar(n)（character varying） 可変長。最大 n 文字。varchar だけなら長さ無制限
text 可変長・長さ無制限。PostgreSQL ではよく使う
  • n はバイト数ではなく文字数
  • ⚠ n を超える文字列を入れると エラー（value too long）。ただし超えた部分がすべて空白なら切り詰めて入る
  • ⚠ CAST('abcdef' AS varchar(3)) のように明示的にキャストすると、エラーにならず切り詰められる（'abc'）

3. 制約 ★★★

制約 内容 NULL の扱い
NOT NULL NULL を禁止 —
UNIQUE 値の重複を禁止 ⚠ NULL は何個でも入る（NULL 同士は等しくないと扱う）
PRIMARY KEY UNIQUE ＋ NOT NULL。1テーブルに1つだけ 入らない
CHECK (条件) 条件を満たさない値を禁止 ⚠ 条件が NULL（UNKNOWN）なら通る（偽のときだけ拒否）
FOREIGN KEY / REFERENCES 参照先テーブルに存在する値だけ許可 NULL は入る
DEFAULT 値 値を省略したときに入る値（厳密には制約ではない） 省略時のデフォルトは NULL
  • PRIMARY KEY・UNIQUE を付けると、自動で一意インデックスが作られる
  • ⚠ 外部キー（参照する側の列）にはインデックスは自動で作られない
  • 外部キーの参照先は主キーか UNIQUE 制約のある列でなければならない

列制約と表制約

CREATE TABLE order_items (
    order_id   integer,
    product_id integer,
    qty        integer NOT NULL,
    PRIMARY KEY (order_id, product_id),                 -- 複合主キー（表制約）
    FOREIGN KEY (product_id) REFERENCES products (id),
    CONSTRAINT qty_positive CHECK (qty > 0)             -- 制約に名前を付ける
);
  • 列制約: 列定義の後ろに書く。その列だけが対象
  • 表制約: 列定義と並べて書く。複数列にまたがる制約（複合主キーなど）はこちらでしか書けない
  • ⚠ NOT NULL は列制約としてしか書けない
  • CONSTRAINT 名前 で制約に名前を付けられる（省略すると自動で付く。削除するときに使う）

外部キーの参照動作

参照先（親）の行を削除・更新したとき、参照元（子）をどうするか。

指定 動作
NO ACTION（デフォルト） 参照されている行は削除・更新できない（エラー）。チェックは文の最後に行う
RESTRICT NO ACTION と同じくエラー。チェックを即座に行う（遅延できない）
CASCADE 子の行も一緒に削除（更新なら子の値も更新）
SET NULL 子の列を NULL にする
SET DEFAULT 子の列をデフォルト値にする 
cat_id integer REFERENCES categories (id) ON DELETE CASCADE ON UPDATE CASCADE

ドメイン（CREATE DOMAIN）

データ型に制約・デフォルト値を付けて名前を付けたもの（ユーザー定義型の一種）。同じ制約を多くの列で使い回せる。

CREATE DOMAIN price_t AS integer
    DEFAULT 0
    NOT NULL
    CHECK (VALUE >= 0);                    -- VALUE は検査対象の値

CREATE TABLE products (
    id    integer PRIMARY KEY,
    price price_t                           -- データ型の代わりに使う
);
  • 付けられるのは NOT NULL / NULL・CHECK・DEFAULT だけ
  • ⚠ UNIQUE・PRIMARY KEY・FOREIGN KEY はドメインに付けられない（列・表の制約として書く）
  • CHECK の中では、検査する値を VALUE で表す（列名は書かない）
  • 列に DEFAULT を書くと、列の DEFAULT がドメインの DEFAULT より優先される
  • ⚠ ドメインの制約は列側で外せない（列側で制約を追加するのはできる）
  • 変更は ALTER DOMAIN（SET DEFAULT / DROP DEFAULT・SET NOT NULL / DROP NOT NULL・ADD CONSTRAINT / DROP CONSTRAINT・RENAME TO）。制約を追加すると既存データも検査され、違反があればエラー
  • DROP DOMAIN d; ⚠ 使っている列があるとエラー。CASCADE ならその列も削除される
  • psql の一覧表示は \dD

列挙型・複合型（CREATE TYPE）

CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');   -- 列挙型
CREATE TYPE address AS (city text, zip text);      -- 複合型（AS の後ろが括弧）

CREATE TABLE people (name text, feel mood, addr address);
INSERT INTO people VALUES ('A', 'happy', ROW('Tokyo', '100-0001'));
SELECT (addr).city FROM people;                    -- 複合型の要素は括弧で囲んで参照
  • 列挙型（ENUM）: 決められた値だけを入れられる型。⚠ 大小比較は定義した順（文字コード順ではない。上の例では 'sad' < 'happy'）
  • 値の追加は ALTER TYPE mood ADD VALUE 'angry';（BEFORE / AFTER で位置指定可）。⚠ 値の削除はできない
  • 複合型: 複数の項目をまとめた型。値は ROW(...) で作る。⚠ 要素の参照は (列名).要素（括弧がないとテーブル名と解釈されエラー）
  • ⚠ 複合型には制約を付けられない（制約を付けたいならドメイン）
  • テーブルを作ると、同じ名前の複合型が自動で作られる
  • DROP TYPE mood;（使っている列があればエラー。CASCADE で列ごと削除）。psql の一覧表示は \dT

4. テーブル定義の変更（ALTER TABLE）★★★

操作 構文
列の追加 ALTER TABLE t ADD COLUMN c integer;（COLUMN は省略可）
列の削除 ALTER TABLE t DROP COLUMN c;
列名の変更 ALTER TABLE t RENAME COLUMN c TO c2;
テーブル名の変更 ALTER TABLE t RENAME TO t2;
データ型の変更 ALTER TABLE t ALTER COLUMN c TYPE bigint;（自動変換できないときは USING 式）
デフォルト値 ALTER TABLE t ALTER COLUMN c SET DEFAULT 0; / DROP DEFAULT
NOT NULL ALTER TABLE t ALTER COLUMN c SET NOT NULL; / DROP NOT NULL
制約の追加 ALTER TABLE t ADD CONSTRAINT 名前 UNIQUE (c);
制約の削除 ALTER TABLE t DROP CONSTRAINT 名前;
  • 追加した列の既存行の値は、DEFAULT 指定があればその値、なければ NULL
  • ⚠ NULL を含む列に SET NOT NULL するとエラー。既存データが制約に違反する ADD CONSTRAINT も同様
  • ⚠ 列名変更は RENAME COLUMN、型変更は ALTER COLUMN ... TYPE。MODIFY（Oracle / MySQL の構文）は使えない
  • カンマで区切れば1文で複数の変更ができる（ALTER TABLE t ADD COLUMN a int, ADD COLUMN b int;）

5. テーブルの削除（DROP / TRUNCATE）★★

DROP TABLE

  • DROP TABLE t; テーブルの定義ごと削除。複数をカンマで並べられる
  • DROP TABLE IF EXISTS t; 存在しなくてもエラーにしない
  • RESTRICT（デフォルト）: 依存するオブジェクト（ビュー・外部キー）があればエラー
  • CASCADE: 依存するオブジェクトも削除
  • ⚠ CASCADE で消えるのはビューや、参照元テーブルの外部キー制約。参照元のテーブル自体は消えない

TRUNCATE

  • TRUNCATE t; テーブルの全行を高速に削除（定義は残る）
  • DELETE（WHERE なし）との違い
DELETE TRUNCATE
WHERE で行を絞る できる できない（常に全行）
速度 行ごとに処理（遅い） テーブルのファイルを作り直す（速い）
領域 不要行が残る → VACUUM で回収 即座に解放
ON DELETE トリガー 実行される 実行されない
ロールバック できる できる（PostgreSQL では TRUNCATE もトランザクション内で取り消せる）
  • RESTART IDENTITY: 列に紐づくシーケンスを初期値に戻す（デフォルトは CONTINUE IDENTITY で戻さない）
  • ⚠ 外部キーで参照されているテーブルは、CASCADE を付けるか参照元も同時に指定しないと TRUNCATE できない（参照元が空でもエラー）

6. データの追加（INSERT）★★★

INSERT INTO products (id, name, price) VALUES (1, 'りんご', 120);
INSERT INTO products VALUES (2, 'みかん', 80, NULL);              -- 列名省略: 全列を定義順に
INSERT INTO products (id, name) VALUES (3, 'ぶどう'), (4, 'もも');  -- 複数行を一度に
INSERT INTO products (id, name, price) VALUES (5, 'なし', DEFAULT); -- デフォルト値を明示
INSERT INTO products_bak SELECT * FROM products WHERE price > 100;  -- 検索結果を追加
INSERT INTO logs DEFAULT VALUES;                                     -- 全列デフォルト値
  • 列リストで省略した列にはデフォルト値（なければ NULL）が入る
  • 列名を省略すると定義順に先頭から当てはめる。値の数が列数より少なければ、残りの列はデフォルト値
  • ⚠ INSERT ... SELECT に VALUES は付けない

RETURNING

  • 追加・更新・削除した行の値をその場で返す（INSERT / UPDATE / DELETE で使える）
  • INSERT INTO products (name) VALUES ('かき') RETURNING id; → 自動採番された id を取得

ON CONFLICT（UPSERT）

一意制約に違反したときの動作を指定する。

INSERT INTO products (id, name, price) VALUES (1, 'りんご', 150)
ON CONFLICT (id) DO UPDATE SET price = EXCLUDED.price;   -- あれば更新、なければ追加

INSERT INTO products (id, name) VALUES (1, 'りんご')
ON CONFLICT DO NOTHING;                                   -- あれば何もしない
  • EXCLUDED は「追加しようとして衝突した行」を指す
  • ⚠ DO UPDATE では衝突対象（(id) や ON CONSTRAINT 制約名）の指定が必須。DO NOTHING は省略できる

7. データの更新・削除（UPDATE / DELETE）★★★

UPDATE products SET price = price * 1.1, name = 'ふじ' WHERE id = 1;
DELETE FROM products WHERE price IS NULL;
  • ⚠ WHERE を省略すると全行が対象（エラーにも警告にもならない）
  • SET の右辺はすべて更新前の値で計算される（SET a = b, b = a で値が入れ替わる）
  • 該当行が0件でもエラーにならない（UPDATE 0 / DELETE 0 と表示）
  • 制約に違反する更新・削除は文全体がエラーになり、1行も変わらない

他のテーブルを参照して更新・削除

-- UPDATE は FROM
UPDATE products p SET price = s.price
FROM sale_prices s WHERE p.id = s.product_id;

-- DELETE は USING
DELETE FROM products p USING discontinued d WHERE p.id = d.product_id;

-- サブクエリでも書ける
DELETE FROM products WHERE id IN (SELECT product_id FROM discontinued);
  • ⚠ 結合に使う句は UPDATE → FROM、DELETE → USING（逆にしない）

1. SELECT の基本と評価順序 ★★★

SELECT   cat_id, count(*) AS cnt        -- 5. 列を選ぶ
FROM     products                        -- 1. 対象テーブル
WHERE    price >= 100                    -- 2. 行を絞る
GROUP BY cat_id                          -- 3. グループ化
HAVING   count(*) >= 2                   -- 4. グループを絞る
ORDER BY cnt DESC                        -- 6. 並べ替え
LIMIT    10;                             -- 7. 件数を制限
  • 評価順: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET
  • ⚠ SELECT で付けた列の別名（AS cnt）は ORDER BY では使えるが、WHERE では使えない（WHERE の時点ではまだ存在しない）
  • AS は省略できる（count(*) cnt）。別名に大文字・空白を含めるときは二重引用符
  • SELECT 1 + 1; のように FROM 句なしでも実行できる（PostgreSQL の特徴）

ORDER BY

  • ORDER BY 列 [ASC | DESC]。デフォルトは ASC（昇順）。列番号（ORDER BY 2）や別名も使える
  • 複数指定すると、前の列が同じ値のときに次の列で並べる
  • ⚠ NULL は最も大きい値として扱う → ASC では最後、DESC では先頭。NULLS FIRST / NULLS LAST で変えられる
  • ORDER BY がないと行の順序は保証されない

LIMIT / OFFSET

  • LIMIT n: 先頭 n 行だけ返す。OFFSET m: 先頭 m 行を飛ばす
  • LIMIT 10 OFFSET 20 → 21〜30行目
  • SQL 標準の書き方: OFFSET 20 ROWS FETCH FIRST 10 ROWS ONLY

DISTINCT

  • SELECT DISTINCT cat_id FROM products; 重複行を1つにまとめる（NULL 同士も1つにまとまる）
  • DISTINCT ON (式): 式の値ごとに先頭の1行だけを返す（PostgreSQL 独自）。ORDER BY の先頭は DISTINCT ON の式と一致させる
-- カテゴリごとに最も高い商品を1件ずつ
SELECT DISTINCT ON (cat_id) cat_id, name, price
FROM products ORDER BY cat_id, price DESC;

2. WHERE の条件 ★★★

演算子 例 意味

3. 集約関数と GROUP BY ★★★

関数 内容 NULL の扱い
count(*) 行数 NULL の行も数える
count(列) 列が NULL でない行の数 NULL を除く
count(DISTINCT 列) 重複を除いた値の数 NULL を除く
sum / avg 合計 / 平均 NULL を除いて計算
max / min 最大 / 最小 NULL を除く
  • ⚠ 対象が0行のとき: count は 0、sum・avg・max・min は NULL
  • ⚠ avg は NULL を分母に含めない（値 10, 20, NULL の avg は 15。20 ではない）
  • 文字列の連結は string_agg(列, ',')、配列にまとめるのは array_agg(列)（→ 04章）

GROUP BY / HAVING

  • GROUP BY の列の値が同じ行を1グループにまとめ、グループごとに集約する
  • ⚠ GROUP BY を使うと、SELECT に書けるのは GROUP BY の列・集約関数・定数だけ（それ以外の列はエラー。ただし GROUP BY に主キーを書いた場合、そのテーブルの他の列は書ける）
  • ⚠ 集約関数は WHERE に書けない → グループに対する条件は HAVING に書く
  • WHERE はグループ化の前に行を絞り、HAVING はグループ化の後にグループを絞る
  • GROUP BY がなくても集約関数を使えば、全体が1グループになる
  • GROUP BY では NULL も1つのグループにまとまる

4. 結合（JOIN）★★★

結合 結果
INNER JOIN（JOIN だけでも同じ） 結合条件に一致する行だけ
LEFT [OUTER] JOIN 左表の全行＋一致する右表の行（なければ右表の列は NULL）
RIGHT [OUTER] JOIN 右表の全行＋一致する左表の行
FULL [OUTER] JOIN 両表の全行（一致しない側は NULL）
CROSS JOIN 直積（全組み合わせ。m 行 × n 行 = m×n 行）。結合条件なし 
SELECT p.name, c.name
FROM products p
LEFT JOIN categories c ON p.cat_id = c.id;

結合条件の書き方

  • ON 条件: 任意の条件
  • USING (列名): 両表の同名の列で等価結合。結果にその列は1つだけ現れる
  • NATURAL JOIN: 同名の列すべてで自動的に等価結合（意図しない列で結合しやすい）
  • 古い書き方: FROM a, b WHERE a.id = b.a_id（カンマは CROSS JOIN と同じ。WHERE で絞ると内部結合と同じ結果）
  • 自己結合: 同じテーブルに別名を付けて結合（FROM emp e JOIN emp m ON e.boss_id = m.id）
  • ⚠ 外部結合で右表の条件を WHERE に書くと、NULL の行が除外されて内部結合と同じ結果になる。残したいときは ON に書く

7. 条件式・CTE・ウィンドウ関数 ★★

CASE

-- 検索 CASE
SELECT name, CASE WHEN price >= 1000 THEN '高' WHEN price >= 100 THEN '中' ELSE '低' END
FROM products;

-- 単純 CASE
SELECT CASE cat_id WHEN 1 THEN '果物' WHEN 2 THEN '野菜' END FROM products;
  • 上の WHEN から順に評価し、最初に真になった THEN を返す
  • ⚠ ELSE を省略して、どれにも当てはまらないと NULL
  • ⚠ 単純 CASE で CASE x WHEN NULL と書いても NULL には一致しない（= で比較するため）

WITH 句（共通テーブル式・CTE）

WITH expensive AS (
    SELECT * FROM products WHERE price >= 1000
)
SELECT cat_id, count(*) FROM expensive GROUP BY cat_id;
  • クエリの中だけで使える名前付きの一時的な結果。サブクエリを読みやすくする
  • WITH RECURSIVE: 自分自身を参照して再帰処理（階層構造の展開、連番の生成など）

ウィンドウ関数

  • 関数() OVER (PARTITION BY 列 ORDER BY 列): 行をまとめずに、グループ内での順位・累計などを各行に付ける
  • 主な関数: row_number()（連番）、rank()（同順位の次は飛ぶ: 1,1,3）、dense_rank()（飛ばない: 1,1,2）、集約関数（sum(price) OVER (...)）
  • ⚠ GROUP BY と違い、行数は減らない

8. スキーマ ★★

  • データベース → スキーマ → テーブルなどのオブジェクト の階層。スキーマはオブジェクトをまとめる名前空間
  • 別のスキーマなら同じ名前のテーブルを作れる。スキーマ名.テーブル名 で指定する
  • 新しいデータベースには public スキーマがある。スキーマを指定しないと public に作られる（通常）
  • ⚠ 別のデータベースのテーブルは1つのクエリで参照できない（スキーマは参照できる）
操作 構文
作成 CREATE SCHEMA s;（AUTHORIZATION ユーザー名 で所有者を指定）
変更 ALTER SCHEMA s RENAME TO s2; / ALTER SCHEMA s OWNER TO alice;
削除 DROP SCHEMA s;（中にオブジェクトがあればエラー。CASCADE で中身ごと削除）

search_path

  • スキーマ名を省略したときに探すスキーマの順番
  • デフォルトは "$user", public（ユーザー名と同じ名前のスキーマ → public）
  • オブジェクトを作るときは、search_path の中で最初に存在するスキーマに作られる
  • 確認: SHOW search_path; 変更: SET search_path TO s, public;
  • システムカタログの pg_catalog スキーマは、search_path に書かなくても常に最初に検索される
  • ⚠ PostgreSQL 14 までは、public スキーマに誰でもオブジェクトを作れる（15 から作成権限が既定で外された）

9. ビュー ★★★

CREATE VIEW expensive_products AS
SELECT id, name, price FROM products WHERE price >= 1000;
  • SELECT 文に名前を付けたもの。データは持たず、参照するたびに元の SELECT を実行する
  • CREATE OR REPLACE VIEW: 既存のビューを置き換える。⚠ ただし列の削除・名前変更・型変更はできず、末尾への列追加だけできる
  • ALTER VIEW v RENAME TO v2;（名前・所有者などの変更）。⚠ 定義（SELECT 文）は ALTER VIEW で変えられない → CREATE OR REPLACE VIEW か作り直し
  • DROP VIEW v;
  • ⚠ ビューが参照しているテーブルは、DROP TABLE ... CASCADE でないと削除できない（CASCADE ならビューも消える）

更新可能ビュー

  • 次の条件を満たす単純なビューは、INSERT / UPDATE / DELETE が自動的に元テーブルへ反映される
    • FROM にテーブル（またはビュー）が1つだけ
    • 集約関数・GROUP BY・HAVING・DISTINCT・LIMIT/OFFSET・UNION 等の集合演算・WITH・ウィンドウ関数を含まない
  • それ以外のビューは、INSTEAD OF トリガーやルールを作れば更新できる
  • WITH CHECK OPTION: ビューの WHERE 条件を満たさない行を、ビュー経由で追加・更新できなくする

マテリアライズドビュー

  • CREATE MATERIALIZED VIEW mv AS SELECT ...; 検索結果を実データとして保存する。参照が速い
  • ⚠ 元テーブルを変更しても自動では反映されない → REFRESH MATERIALIZED VIEW mv; で更新
  • インデックスを作れる。直接 INSERT / UPDATE はできない

10. インデックス ★★★

CREATE INDEX idx_products_name ON products (name);
CREATE UNIQUE INDEX idx_products_code ON products (code);    -- 一意インデックス
CREATE INDEX ON products (cat_id, price);                     -- 複数列。名前は省略可（自動命名）
CREATE INDEX idx_lower_name ON products (lower(name));        -- 式インデックス
CREATE INDEX idx_active ON products (name) WHERE deleted = false;  -- 部分インデックス
CREATE INDEX idx_tags ON products USING gin (tags);           -- 方式の指定
DROP INDEX idx_products_name;
  • 検索（WHERE・JOIN・ORDER BY）を速くする。代わりに更新は遅くなり、領域を使う
  • デフォルトの方式は B-tree（等価・範囲検索・ソートに使える）
  • 式インデックス: WHERE lower(name) = 'abc' のように同じ式で検索したときに使われる
  • 部分インデックス: 条件に合う行だけを索引に入れる
  • CREATE INDEX CONCURRENTLY: テーブルへの書き込みを止めずに作成（時間はかかる。トランザクションブロック内では実行できない）
  • REINDEX INDEX 名前; / REINDEX TABLE t; でインデックスを作り直す
  • ALTER INDEX 名前 RENAME TO 新名; / ALTER INDEX 名前 SET TABLESPACE ts;。⚠ 対象の列や式は ALTER INDEX で変えられない → 作り直す
  • ⚠ LIKE 'abc%'（前方一致）は B-tree が使える場合があるが、LIKE '%abc'（後方・中間一致）は B-tree を使えない
  • ⚠ インデックスはテーブルに属し、DROP TABLE で一緒に削除される

11. シーケンスと自動採番 ★★★

シーケンス

CREATE SEQUENCE seq_order START 100 INCREMENT 10;
SELECT nextval('seq_order');    -- 100
SELECT nextval('seq_order');    -- 110
SELECT currval('seq_order');    -- 110（このセッションで最後に nextval した値）
SELECT setval('seq_order', 500);  -- 次の nextval は 510
関数 動作
nextval('名前') 値を進めて返す
currval('名前') そのセッションで最後に nextval が返した値。⚠ セッション内で一度も nextval していないとエラー
lastval() そのセッションで最後に使った（どれかの）シーケンスの値
setval('名前', n) 現在値を n にする → 次の nextval は n + 増分。setval('名前', n, false) なら次の nextval は n
  • オプション: START（初期値・デフォルト1）、INCREMENT（増分・負も可）、MINVALUE、MAXVALUE、CYCLE（最大値に達したら最小値に戻る。デフォルトは NO CYCLE で、達するとエラー）、CACHE
  • 変更は ALTER SEQUENCE（INCREMENT などのオプションを変える）。ALTER SEQUENCE seq RESTART WITH 1; で番号を振り直す（WITH 省略なら START の値から）
  • DROP SEQUENCE seq;
  • ⚠ nextval はロールバックしても戻らない → 番号に欠番が出る
  • 複数のセッションが同時に nextval しても、同じ値は返らない

serial 型

CREATE TABLE orders (id serial PRIMARY KEY, ...);
  • 次の3つをまとめて行う略記: ① integer 列を作る ② シーケンス orders_id_seq を作る ③ 列の DEFAULT を nextval('orders_id_seq') にし、NOT NULL を付ける
  • ⚠ serial だけでは UNIQUE / PRIMARY KEY は付かない（重複を防ぐには別途指定）
  • ⚠ 値を明示的に指定して INSERT できる（シーケンスは進まない → 後で重複エラーの原因になる）
  • 列（テーブル）を削除すると、シーケンスも削除される

IDENTITY 列（SQL 標準）

id integer GENERATED ALWAYS AS IDENTITY       -- 明示的な値の指定を拒否
id integer GENERATED BY DEFAULT AS IDENTITY   -- 値を指定すればそれを使う
  • ALWAYS: INSERT で値を指定するとエラー（OVERRIDING SYSTEM VALUE を付ければ指定できる）
  • BY DEFAULT: 値を省略したときだけ自動採番（serial に近い）
  • IDENTITY 列には自動で NOT NULL が付く

12. パーティショニング ★

CREATE TABLE sales (sold_on date, amount integer) PARTITION BY RANGE (sold_on);
CREATE TABLE sales_2026 PARTITION OF sales
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
  • 大きなテーブルを、キーの値で複数の子テーブル（パーティション）に分ける（宣言的パーティショニング）
  • 方式: RANGE（範囲）、LIST（値の列挙: FOR VALUES IN ('東京', '大阪')）、HASH（ハッシュ値で均等に分散）
  • ⚠ RANGE の FROM ... TO ... は FROM を含み、TO を含まない
  • 親テーブルに INSERT すると、適切なパーティションに自動で振り分けられる。行き先のパーティションがなければエラー（DEFAULT パーティションを作れば受け止められる）

パーティションの付け外し（ATTACH / DETACH）

ALTER TABLE sales ATTACH PARTITION sales_2027
    FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');   -- 既存テーブルを子にする
ALTER TABLE sales DETACH PARTITION sales_2026;          -- 子を切り離す
  • ATTACH: 作ってある普通のテーブルをパーティションとして組み込む。⚠ 範囲に合わない行があるとエラー（組み込む前に全行を検査する）
  • DETACH: パーティションを親から外す。⚠ 外したテーブルは独立したテーブルとして残る（データは消えない。消したいなら DROP TABLE）
  • 古いデータの切り離し → 退避・削除が、DELETE より速く済む

13. 関数・プロシージャ・トリガー ★★

ユーザー定義関数

CREATE FUNCTION tax_in(price integer) RETURNS integer AS $$
    SELECT (price * 1.1)::integer;
$$ LANGUAGE sql;

SELECT tax_in(100);   -- 110
  • CREATE [OR REPLACE] FUNCTION 名前(引数) RETURNS 戻り値の型 AS 本体 LANGUAGE 言語;
  • 本体は文字列。ドル引用符 $$ ... $$ を使うと中の単一引用符をエスケープしなくてよい
  • 言語: sql、plpgsql（変数・IF・ループが使える）、C など
  • RETURNS void（返り値なし）、RETURNS SETOF 型 / RETURNS TABLE (...)（複数行を返す）
  • 同じ名前でも引数の型・数が違えば別の関数として作れる（オーバーロード）。削除時は DROP FUNCTION tax_in(integer); のように引数の型で区別する
  • プロシージャ: CREATE PROCEDURE で作り CALL で実行。戻り値を持たず、中で COMMIT / ROLLBACK できる（関数はできない）

PL/pgSQL の基本形

CREATE FUNCTION grade(score integer) RETURNS text AS $$
DECLARE
    result text;
BEGIN
    IF score >= 80 THEN
        result := 'A';
    ELSE
        result := 'B';
    END IF;
    RETURN result;
END;
$$ LANGUAGE plpgsql;

トリガー

テーブルへの INSERT / UPDATE / DELETE（/ TRUNCATE）をきっかけに、関数を自動実行する。

CREATE FUNCTION set_updated() RETURNS trigger AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_updated BEFORE UPDATE ON products
    FOR EACH ROW EXECUTE FUNCTION set_updated();
  • 手順: ① 戻り値の型が trigger の関数を作る（引数なし）→ ② CREATE TRIGGER でテーブルに紐づける
  • タイミング: BEFORE（実行前）/ AFTER（実行後）/ INSTEAD OF（ビューに対してのみ。代わりに実行）
  • 単位: FOR EACH ROW（1行ごと）/ FOR EACH STATEMENT（1文に1回。デフォルト）
  • 行トリガーでは NEW（新しい行。INSERT・UPDATE）と OLD（古い行。UPDATE・DELETE）を参照できる
  • ⚠ BEFORE の行トリガーが NULL を返すと、その行の操作は行われない。NEW を書き換えて返すと、書き換えた値で保存される
  • AFTER トリガーや文単位トリガーの戻り値は無視される
  • EXECUTE PROCEDURE は古い書き方（意味は同じ）。DROP TRIGGER trg_updated ON products;

8. トランザクションの基本 ★★★

開始・確定・取り消し

操作 コマンド（同じ意味の別名）
開始 BEGIN / START TRANSACTION
確定 COMMIT / END
取り消し ROLLBACK / ABORT
  • psql はデフォルトで自動コミット（AUTOCOMMIT が on）: BEGIN しなければ1文ごとに自動で COMMIT される
  • psql で \set AUTOCOMMIT off にすると、最初の文で自動的にトランザクションが始まり、COMMIT するまで確定しない
  • トランザクション外で COMMIT / ROLLBACK を実行してもエラーにならない（WARNING: there is no transaction in progress）

エラーが起きたとき

BEGIN;
INSERT INTO t VALUES (1);
INSERT INTO t VALUES ('abc');   -- エラー
INSERT INTO t VALUES (2);
-- ERROR:  current transaction is aborted, commands ignored until end of transaction block
COMMIT;                          -- 実際には ROLLBACK される（1 も入らない）
  • ⚠ トランザクション内でエラーが起きると、以降の文はすべて拒否される（アボート状態）
  • ⚠ この状態で COMMIT しても ROLLBACK になる（表示も ROLLBACK）。エラー前の文も含めて全部取り消される
  • 抜け出すには ROLLBACK（またはセーブポイントへのロールバック）

セーブポイント

BEGIN;
INSERT INTO t VALUES (1);
SAVEPOINT sp1;
INSERT INTO t VALUES (2);
ROLLBACK TO SAVEPOINT sp1;   -- 2 の INSERT だけ取り消す（SAVEPOINT は省略可）
INSERT INTO t VALUES (3);
COMMIT;                      -- 1 と 3 が確定
  • SAVEPOINT 名前: トランザクション内に中間地点を作る
  • ROLLBACK TO [SAVEPOINT] 名前: その地点まで戻す。トランザクションは続く（セーブポイント自体も残る）
  • RELEASE [SAVEPOINT] 名前: セーブポイントを破棄する（それまでの変更は取り消されない）
  • エラーでアボート状態になっても、エラー前のセーブポイントへ ROLLBACK TO すれば続行できる
  • ⚠ セーブポイントはトランザクションブロックの中でしか使えない

トランザクションと DDL

  • PostgreSQL では CREATE TABLE・DROP TABLE・TRUNCATE などの DDL もロールバックできる
  • ⚠ 例外: CREATE DATABASE / DROP DATABASE、CREATE TABLESPACE / DROP TABLESPACE、VACUUM、ALTER SYSTEM、CREATE INDEX CONCURRENTLY はトランザクションブロック内で実行できない（エラー）
  • ⚠ シーケンスの nextval はロールバックしても戻らない（→ 03章）

9. トランザクション分離レベル ★★★

同時実行で起きる現象

現象 別名・英語表記 内容
ダーティリード Dirty Read（P1） 他のトランザクションがコミットしていない変更が読めてしまう
ノンリピータブルリード Non-Repeatable Read、ファジーリード（Fuzzy Read）（P2） 同じ行を2回読むと、間に他がコミットした更新・削除のせいで値が変わる
ファントムリード Phantom Read（P3） 同じ条件で2回検索すると、間に他がコミットした追加のせいで行が増える（減る）
直列化異常 Serialization Anomaly 同時に実行した結果が、どの順番で1つずつ実行した結果とも一致しない
  • ⚠ 「ファジーリード」と「ノンリピータブルリード」は同じ現象。選択肢で別々の現象のように並んでいても混同しない
  • ノンリピータブルリードは「同じ行の値が変わる」、ファントムリードは「行の集合が変わる」で区別する
  • P0〜P3 は論文（Berenson ほか 1995「A Critique of ANSI SQL Isolation Levels」）での番号。P0 はダーティライト（未コミットの変更を上書き）で、PostgreSQL ではどの分離レベルでも起きない

分離レベルと PostgreSQL の動作

分離レベル ダーティリード ノンリピータブルリード ファントムリード 直列化異常
READ UNCOMMITTED 起きない（※） 起きる 起きる 起きる
READ COMMITTED（デフォルト） 起きない 起きる 起きる 起きる
REPEATABLE READ 起きない 起きない 起きない（※） 起きる
SERIALIZABLE 起きない 起きない 起きない 起きない
  • ⚠ PostgreSQL のデフォルトは READ COMMITTED
  • ⚠ ※ PostgreSQL では READ UNCOMMITTED を指定しても READ COMMITTED として動く（ダーティリードはどのレベルでも起きない）
  • ⚠ ※ SQL 標準では REPEATABLE READ でファントムリードが起きてもよいが、PostgreSQL の REPEATABLE READ では起きない
  • READ COMMITTED: 文ごとに、その文の開始時点でコミット済みのデータを見る
  • REPEATABLE READ / SERIALIZABLE: トランザクション内の最初の文の開始時点のデータをずっと見る
  • REPEATABLE READ / SERIALIZABLE では、他と競合すると「could not serialize access ...」のエラーになる → アプリ側でトランザクションを最初からやり直す

設定方法

BEGIN ISOLATION LEVEL SERIALIZABLE;              -- 開始時に指定
-- または
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; -- 最初の文より前に実行
  • ⚠ SET TRANSACTION は、トランザクション内で SELECT や INSERT などを実行した後では変更できない（エラー）
  • セッション全体のデフォルト: SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL ...; またはパラメータ default_transaction_isolation（postgresql.conf でも設定可）
  • 確認: SHOW transaction_isolation;

10. ロック ★★

MVCC とロックの関係

  • PostgreSQL は MVCC なので、読み取り（SELECT）と書き込み（UPDATE など）は互いを待たない
  • 同じ行を2つのトランザクションが更新しようとすると、後の方は先の方がコミット / ロールバックするまで待たされる（行ロック）
  • ⚠ ただし ACCESS EXCLUSIVE ロック（DROP TABLE・TRUNCATE・VACUUM FULL・多くの ALTER TABLE）は SELECT もブロックする

主なテーブルロックのモード

ロックモード 取得する主なコマンド
ACCESS SHARE SELECT
ROW SHARE SELECT ... FOR UPDATE / FOR SHARE
ROW EXCLUSIVE INSERT・UPDATE・DELETE
SHARE UPDATE EXCLUSIVE VACUUM（FULL なし）、ANALYZE、CREATE INDEX CONCURRENTLY
SHARE CREATE INDEX（CONCURRENTLY なし）
SHARE ROW EXCLUSIVE CREATE TRIGGER など
EXCLUSIVE REFRESH MATERIALIZED VIEW CONCURRENTLY
ACCESS EXCLUSIVE DROP TABLE、TRUNCATE、VACUUM FULL、ALTER TABLE（多く）、LOCK TABLE（モード省略時）
  • 下に行くほど強い。ACCESS EXCLUSIVE は他のすべてのロックと競合する
  • ⚠ CREATE INDEX（SHARE）は書き込みを止めるが読み取りは止めない。書き込みも止めたくないときは CONCURRENTLY

明示的なロック

  • LOCK TABLE t IN 〜 MODE;: テーブルロックを取る。モードを省略すると ACCESS EXCLUSIVE
    • ⚠ トランザクションブロックの中でしか使えない。ロックはトランザクション終了時に解放される（個別に解放する UNLOCK コマンドはない）
  • SELECT ... FOR UPDATE: 読んだ行に更新用の行ロックをかける（他は更新・削除・FOR UPDATE できず待つ）
    • FOR SHARE: 共有ロック（他の FOR SHARE は可、更新は不可）
    • NOWAIT: ロックが取れなければ待たずにエラー
    • SKIP LOCKED: ロックされている行を飛ばして返す

デッドロック

  • 2つのトランザクションが互いに相手のロック解放を待つ状態
  • PostgreSQL は自動で検出し、片方のトランザクションをエラーにしてロールバックさせる（もう片方は続行できる）
  • 検出のチェックを始めるまでの待ち時間はパラメータ deadlock_timeout（デフォルト 1秒）
  • 防ぐには、複数の行・テーブルを同じ順番でロックするようにする
  • 現在のロックの状況はシステムビュー pg_locks で確認できる

2. データベースクラスタと initdb ★★★

データベースクラスタ

  • 1つのサーバ（postgres プロセス群）が管理するデータベースの集まり。ディスク上では1つのディレクトリ（データディレクトリ）
  • ⚠ 「クラスタ」は複数サーバの集合のことではない。1インスタンスが管理するデータベース群
  • initdb 直後に作られるデータベース: template0、template1、postgres の3つ
    • template1: CREATE DATABASE のデフォルトの複製元（→ 08章）
    • template0: 変更してはいけない素のテンプレート
    • postgres: 接続先がないときに使うデフォルトのデータベース

モード 動作 シグナル

2. postgresql.conf の書式 ★★

# コメント
listen_addresses = '*'        # 文字列は単引用符で囲む
port = 5432
shared_buffers = 256MB        # 単位付きで書ける
log_min_duration_statement = 1s
autovacuum = on
  • パラメータ名 = 値（= は省略可）。# 以降はコメント
  • パラメータ名は大文字・小文字を区別しない
  • ⚠ 同じパラメータを複数回書くと最後に書いたものが有効
  • 行頭を # でコメントアウトした（書かれていない）パラメータはデフォルト値になる
  • 値の型
    • 真偽値: on / off、true / false、yes / no、1 / 0
    • メモリの単位: kB、MB、GB、TB（1024 倍。大文字・小文字を区別する。mb は不可）
    • 時間の単位: us、ms、s、min、h、d
    • 単位を省略すると、パラメータごとに決まった単位（例: shared_buffers は 8kB ブロック、work_mem は kB）
  • 別ファイルの取り込み: include 'ファイル'、include_if_exists 'ファイル'（無くてもエラーにしない）、include_dir 'ディレクトリ'（中の .conf を名前順に読む）

3. パラメータの反映方法 ★★★

context（変更できるタイミング）

context 変更の反映 例
postmaster サーバの再起動が必要 listen_addresses、port、max_connections、shared_buffers、wal_level、archive_mode、logging_collector
sighup 設定の再読み込み（reload）で反映。セッション内の SET は不可 log_（多く）、archive_command、autovacuum、checkpoint_timeout、pg_hba.conf の内容*

  • pg_settings の pending_restart 列: 設定ファイルは変えたが再起動しないと反映されないパラメータが true になる

再読み込みの方法

方法
pg_ctl reload OS のコマンドから
SELECT pg_reload_conf(); SQL から（スーパーユーザーなど）
kill -HUP <postmaster の PID> シグナルを直接送る
systemctl reload postgresql-14 パッケージ版のサービスから

4. SQL からの設定変更 ★★★

セッション単位: SET / SHOW / RESET

SET work_mem = '64MB';            -- このセッションだけ変更（TO も可: SET work_mem TO '64MB'）
SHOW work_mem;                    -- 現在値を表示
SHOW ALL;                         -- 全パラメータ
RESET work_mem;                   -- デフォルト（設定ファイルの値）に戻す
SET LOCAL work_mem = '128MB';     -- このトランザクションの間だけ変更
SELECT current_setting('work_mem');          -- 関数で取得
SELECT set_config('work_mem', '32MB', false); -- 関数で設定（true ならトランザクション内だけ）
  • ⚠ SET の効果はそのセッションだけ。切断すると消え、他のセッションには影響しない
  • ⚠ SET LOCAL はトランザクションの終了で元に戻る。トランザクション外で使うと警告が出て効果なし
  • トランザクション内で SET した後に ROLLBACK すると SET も取り消される

永続的な変更: ALTER SYSTEM

ALTER SYSTEM SET work_mem = '16MB';   -- postgresql.auto.conf に書き込む
SELECT pg_reload_conf();              -- 反映（postmaster のパラメータなら再起動）
ALTER SYSTEM RESET work_mem;          -- auto.conf から削除
ALTER SYSTEM RESET ALL;
  • スーパーユーザーだけが実行できる
  • ⚠ ALTER SYSTEM はファイルに書くだけ。反映には再読み込みか再起動が必要
  • ⚠ トランザクションブロック内では実行できない
  • ⚠ postgresql.auto.conf は postgresql.conf より後に読まれるので、同じパラメータは auto.conf の値が勝つ

データベース単位・ロール単位

ALTER DATABASE sampledb SET work_mem = '32MB';
ALTER ROLE alice SET search_path = 'app, public';
ALTER ROLE alice IN DATABASE sampledb SET work_mem = '64MB';
ALTER ROLE alice RESET work_mem;
  • 次に接続したセッションから有効（今のセッションには効かない）
  • 設定値の優先順位（後ろほど優先）
postgresql.conf → postgresql.auto.conf → サーバ起動オプション（postgres -c）
  → ALTER DATABASE ... SET → ALTER ROLE ... SET → ALTER ROLE ... IN DATABASE ... SET
  → クライアントの接続オプション（PGOPTIONS） → セッション内の SET

6. pg_hba.conf（クライアント認証） ★★★

書式

# TYPE    DATABASE   USER       ADDRESS           METHOD
local     all        postgres                     peer
local     all        all                          scram-sha-256
host      all        all        127.0.0.1/32      scram-sha-256
host      sampledb   +staff     192.168.1.0/24    scram-sha-256
hostssl   all        all        0.0.0.0/0         scram-sha-256
host      all        all        ::1/128           scram-sha-256
host      replication  repuser  192.168.1.20/32   scram-sha-256
host      all        all        0.0.0.0/0         reject
  • 1行1ルール。接続タイプ データベース ユーザー [アドレス] 認証方式 [オプション]
  • 上から順に評価し、最初に一致した行だけを使う
  • ⚠ 一致した行の認証に失敗しても、次の行は試さない（そのまま接続拒否）
  • ⚠ どの行にも一致しなければ拒否
  • ⚠ 書く順番が大事: 例外的なルール（特定ユーザーの許可・拒否）は上に、一般的なルールは下に書く
  • 変更は 再読み込み（pg_ctl reload / pg_reload_conf()） で反映
  • 中身の確認: システムビュー pg_hba_file_rules（書式エラーの行も分かる）

接続タイプ（TYPE）

タイプ 対象
local Unix ドメインソケットの接続（アドレス欄は書かない）
host TCP/IP の接続（SSL・非 SSL の両方）
hostssl TCP/IP のうち SSL を使う接続だけ
hostnossl TCP/IP のうち SSL を使わない接続だけ
hostgssenc / hostnogssenc GSSAPI 暗号化の有無
  • ⚠ psql -h localhost は TCP/IP（host 行）、-h なしは Unix ドメインソケット（local 行） になる

データベース（DATABASE）とユーザー（USER）

書き方 意味
all すべて。⚠ DATABASE の all に replication は含まれない
sameuser ユーザー名と同じ名前のデータベース
samerole ユーザーが同名のロールのメンバーであるデータベース
replication 物理レプリケーション接続（pg_basebackup など）
名前 そのデータベース / ユーザー。カンマ区切りで複数可
+ロール名（USER 欄） そのロールのメンバー全員
@ファイル名 ファイルに書いた名前の一覧

アドレス（ADDRESS）

  • CIDR 形式: 192.168.1.0/24（ネットワーク）、192.168.1.10/32（1台）、0.0.0.0/0（IPv4 すべて）、::1/128（IPv6 のループバック）
  • IP アドレスとネットマスクを2列に分けて書いてもよい（192.168.1.0 255.255.255.0）
  • samehost（サーバ自身のアドレス）、samenet（サーバと同じサブネット）、ホスト名も書ける

認証方式（METHOD）

方式 動作
trust 無条件で許可（パスワード不要）
reject 無条件で拒否
scram-sha-256 SCRAM-SHA-256 のパスワード認証（最も安全なパスワード方式）
md5 MD5 のチャレンジ・レスポンス認証。保存されたパスワードが SCRAM 形式なら自動で SCRAM 認証になる
password パスワードを平文で送る（SSL なしでは非推奨）
peer OS のユーザー名をカーネルから取得し、DB ユーザー名と同じなら許可。local 接続専用
ident ident サーバに問い合わせて OS ユーザー名を得る（TCP/IP 用。local 指定時は peer になる）
ldap / radius / pam / gss / sspi / cert 外部の認証基盤・証明書による認証
  • ⚠ trust はパスワードなしで誰でも入れる。initdb のデフォルト（-A 省略時）は trust
  • ⚠ md5 方式でも、password_encryption = scram-sha-256（14 のデフォルト）で設定したパスワードなら SCRAM で認証される。逆に、MD5 形式で保存されたパスワードは scram-sha-256 方式では認証できない
  • ⚠ peer は local 接続でしか使えない
  • オプション: map=マップ名 で pg_ident.conf のマップを使い、OS ユーザー名と違う DB ユーザー名を許可できる
# pg_ident.conf
# MAPNAME   SYSTEM-USERNAME   PG-USERNAME
mymap       taro              app_user

# pg_hba.conf
local   all   app_user   peer   map=mymap

バックアップ

S2.4 バックアップ方法（重要度7）。7問前後で、運用管理で最大の山。pg_dump の出力形式とリストア方法の組み合わせ、COPY と \copy の違い、PITR の手順が定番。

1. バックアップ方法の全体像 ★★★

方法 種類 サーバ 単位 主なツール
論理バックアップ SQL やデータの形でダンプ 起動したまま データベース / テーブル pg_dump、pg_dumpall
物理バックアップ（オフライン） データディレクトリのファイルをコピー 停止して クラスタ全体 cp、tar、rsync
物理バックアップ（オンライン） 起動したままファイルをコピー 起動したまま クラスタ全体 pg_basebackup、低レベル API
PITR オンライン物理バックアップ + WAL アーカイブ 起動したまま クラスタ全体 上記 + archive_command
COPY テーブルのデータだけをファイルへ 起動したまま テーブル COPY、\copy
  • ⚠ 論理バックアップは別のメジャーバージョン・別の OS / CPU アーキテクチャへ移せる。物理バックアップは同じメジャーバージョン・同じアーキテクチャでしか使えない
  • ⚠ 論理バックアップは取得した時点にしか戻せない。任意の時点に戻せるのは PITR
  • 物理バックアップはテーブル単位では戻せない（クラスタ全体を戻す）

2. pg_dump ★★★

pg_dump [接続オプション] [オプション] データベース名
  • 1つのデータベースを論理バックアップする。サーバを起動したまま取得でき、取得中も他のユーザーは読み書きできる
  • 取得開始時点の一貫したスナップショットを出力する（途中の更新は含まない）
  • ⚠ pg_dump は対象テーブルに ACCESS SHARE ロックを取るので、取得中は DROP TABLE や ALTER TABLE など（ACCESS EXCLUSIVE）が待たされる
  • 実行するユーザーには対象の読み取り権限が必要（通常はスーパーユーザーで実行）

出力形式（-F）

オプション 形式 リストア方法 特徴
-Fp（デフォルト） プレーンテキスト（SQL スクリプト） psql 中身を読める・編集できる
-Fc カスタム形式 pg_restore デフォルトで圧縮。リストア時にオブジェクトを選べる・並べ替えられる
-Fd ディレクトリ形式 pg_restore テーブルごとにファイル。並列ダンプ（-j）できる唯一の形式
-Ft tar 形式 pg_restore 圧縮はできない
  • ⚠ プレーンテキストは pg_restore では戻せない（psql で流す）。それ以外の3形式は psql では戻せない（pg_restore を使う）
  • ⚠ pg_dump の並列実行（-j）はディレクトリ形式だけ。pg_restore の -j はカスタム形式とディレクトリ形式で使える

-t テーブル / -T テーブル そのテーブルだけ / そのテーブルを除いて出力
-n スキーマ / -N スキーマ そのスキーマだけ / 除いて出力

-O / --no-owner 所有者を設定する文を出力しない
-x / --no-privileges GRANT / REVOKE を出力しない
-Z 0〜9 圧縮レベル
-j 数 並列数（-Fd のみ）
  • ⚠ -s（schema-only）の「schema」はスキーマ（名前空間）ではなく「定義」。スキーマを選ぶのは -n
  • ⚠ データはデフォルトで COPY 文として出力される

pg_dump が出力しないもの

  • ⚠ ロール（ユーザー）とテーブルスペースはクラスタ全体のオブジェクト（グローバルオブジェクト）なので、pg_dump では出力されない → pg_dumpall を使う
  • データベース自体の作成文（CREATE DATABASE）も、-C を付けない限り出力しない

  • ⚠ 出力はプレーンテキストだけ（-F オプションがない）→ リストアは psql

4. リストア（psql と pg_restore） ★★★

5. COPY と \copy ★★★

  • COPY FROM はトリガーや制約チェックを実行する

6. 物理バックアップ ★★

オフラインバックアップ（コールドバックアップ）

  1. サーバを停止する（pg_ctl stop）
  2. データディレクトリ全体（テーブルスペースを使っていればその実体も）を tar や cp でコピーする
  3. サーバを起動する
  • ⚠ 起動したままデータディレクトリを単純コピーしても、一貫したバックアップにはならない
  • ⚠ 一部のデータベース・テーブルだけを戻すことはできない（クラスタ全体を戻す）

pg_basebackup（オンラインバックアップ）

pg_basebackup -D /backup/base -Fp -X stream -P -U repuser -h 192.168.1.10
  • サーバを起動したまま、クラスタ全体の物理バックアップを取る（レプリケーション接続を使う）
  • ストリーミングレプリケーションのスタンバイ構築にも使う
オプション 意味
-D ディレクトリ 出力先（必須）。⚠ 空か存在しないこと
-F p / -F t plain（データディレクトリと同じ構成。デフォルト）/ tar
-X 方式 バックアップ中の WAL の取得方法: stream（デフォルト。並行して転送）/ fetch（最後にまとめて）/ none
-z gzip 圧縮（tar 形式）
-P 進捗を表示
-R スタンバイ用の設定（standby.signal と、postgresql.auto.conf への primary_conninfo）を書き出す
-c fast / -c spread 開始時のチェックポイントを即時 / 分散（デフォルト spread）
-l ラベル バックアップのラベル
  • 必要な条件
    • wal_level が replica 以上（デフォルトの replica で OK）
    • max_wal_senders が 1 以上（デフォルト 10）
    • 接続ロールに REPLICATION 属性（またはスーパーユーザー）
    • pg_hba.conf に DATABASE = replication の行
  • ⚠ pg_hba.conf の DATABASE 欄が all でもレプリケーション接続には一致しない。replication と書く

低レベル API（PostgreSQL 14）

SELECT pg_start_backup('label');   -- バックアップ開始（チェックポイントを実行）
-- この間に OS のコマンドでデータディレクトリをコピー
SELECT pg_stop_backup();           -- バックアップ終了（必要な WAL のアーカイブを待つ）
  • 開始すると、データディレクトリに backup_label ファイル（開始位置などの情報）ができる（排他モードの場合）
  • ⚠ 15 で pg_backup_start() / pg_backup_stop() に改名され、排他モードは廃止。試験（14 基準）は旧名で答える

7. WAL とアーカイブ ★★★

WAL の基本

  • WAL（Write Ahead Log、先行書き込みログ）: データを変更する前に、変更内容をログに書く仕組み
  • コミット時は WAL をディスクに書けばよく、データファイルへの反映はチェックポイントでまとめて行う
  • WAL ファイルは pg_wal/ に置かれ、1ファイル（WAL セグメント）は 16MB（initdb の --wal-segsize で変更可）
  • ファイル名は 24桁の16進数（タイムライン ID 8桁 + 論理位置 16桁）。例: 000000010000000000000003
  • WAL 内の位置は LSN（Log Sequence Number）。SELECT pg_current_wal_lsn(); で確認
  • 使い終わった WAL は、チェックポイント後に削除または再利用される → PITR にはアーカイブして残しておく必要がある
  • SELECT pg_switch_wal();: 現在の WAL ファイルを閉じて次のファイルへ切り替える（すぐにアーカイブさせたいとき。10 より前は pg_switch_xlog）

WAL アーカイブの設定（postgresql.conf）

wal_level = replica                       # minimal では不可
archive_mode = on                         # 変更は再起動が必要
archive_command = 'cp %p /archive/%f'     # 変更は再読み込みで反映
archive_timeout = 60                      # 任意。この秒数ごとに強制的に WAL を切り替える
記号 意味
%p アーカイブする WAL ファイルのパス（データディレクトリからの相対パス）
%f WAL ファイルのファイル名だけ
  • archive_command は WAL ファイルが一杯になる（切り替わる）たびに実行される
  • ⚠ コマンドが終了ステータス 0 を返したときだけ成功とみなす。失敗した WAL は pg_wal に残り、成功するまで再試行される（pg_wal があふれるおそれ）
  • ⚠ archive_mode の変更は再起動、archive_command の変更は再読み込みで反映
  • アーカイブの状況はシステムビュー pg_stat_archiver で確認できる

8. PITR（ポイントインタイムリカバリ） ★★★

仕組み

  • ベースバックアップ（オンライン物理バックアップ）を戻し、その後の アーカイブ WAL を再生（ロールフォワード） して、任意の時点まで復旧する
  • 例: 誤って DROP TABLE した直前の時刻まで戻せる

事前準備

  1. WAL アーカイブを有効にする（wal_level・archive_mode・archive_command）
  2. 定期的に ベースバックアップ（pg_basebackup など）を取る

リカバリの手順（PostgreSQL 12 以降）

  1. サーバを停止する
  2. 現在のデータディレクトリを退避し、ベースバックアップを戻す
  3. 退避した pg_wal/ のうち、まだアーカイブされていない WAL を新しい pg_wal/ にコピーする（最新まで戻すため）
  4. postgresql.conf（または postgresql.auto.conf）に restore_command と、必要ならリカバリ目標を書く
  5. データディレクトリに recovery.signal ファイル（空でよい）を作る
  6. サーバを起動する → WAL を再生してリカバリ → 完了すると通常運転になる（recovery.signal は自動で削除される）
restore_command = 'cp /archive/%f %p'          # アーカイブから WAL を取り出すコマンド
recovery_target_time = '2026-11-25 10:29:00'    # この時刻まで戻す
  • ⚠ 12 以降は recovery.conf が廃止され、設定は postgresql.conf に、リカバリ開始の合図は recovery.signal ファイルになった（recovery.conf があると起動しない）
  • standby.signal: リカバリ後もスタンバイとして WAL の再生を続ける（ストリーミングレプリケーション用）
  • リカバリが完了すると新しいタイムラインが始まる（WAL ファイル名の先頭8桁が増える）。過去の時点に戻した後の歴史を、元の歴史と区別するため

リカバリ目標のパラメータ

パラメータ 意味
recovery_target_time 指定した時刻まで
recovery_target_xid 指定したトランザクション ID まで
recovery_target_name pg_create_restore_point('名前') で作った復元ポイントまで
recovery_target_lsn 指定した LSN まで
recovery_target = 'immediate' ベースバックアップが一貫性のある状態になった時点で止める
recovery_target_inclusive 目標のちょうどその点を含めるか（デフォルト on = 含める）
recovery_target_timeline どのタイムラインに沿って戻すか（12 からデフォルト latest）
recovery_target_action 目標に達した後の動作: pause（デフォルト）/ promote / shutdown
  • ⚠ 目標を何も指定しないと、アーカイブの最後（最新）まで再生する
  • ⚠ 目標のパラメータは1つだけ指定できる（複数書くとエラー）
  • pause で止まったら、内容を確認してから SELECT pg_wal_replay_resume(); でリカバリを終えて通常運転にする

運用管理作業

S2.5 基本的な運用管理作業（重要度7）。7問前後。VACUUM と VACUUM FULL の違い、autovacuum、ロールと GRANT / REVOKE、テーブルスペース、システムカタログが定番。

1. VACUUM ★★★

なぜ必要か

  • PostgreSQL は MVCC: UPDATE は「古い行を無効にして新しい行を追加」、DELETE は「行を無効にする」だけで、古い行（不要タプル / dead tuple）が物理的に残る
  • 放っておくとテーブルが膨れ（肥大化）、検索が遅くなる → VACUUM で不要な行の領域を回収する
  • VACUUM の役割
    1. 不要タプルの領域を再利用できるようにする
    2. 可視性マップを更新する（Index Only Scan を速くする）
    3. トランザクション ID の周回（wraparound）を防ぐ（古い行を凍結 = FREEZE する）
    4. ANALYZE を付ければ統計情報も更新

VACUUM と VACUUM FULL

VACUUM（通常） VACUUM FULL
動作 不要領域を再利用可能にする テーブルを新しいファイルに書き直して詰める
ディスク容量 OS には基本返さない（末尾の空きページだけ返す） OS に返す（ファイルが小さくなる）
ロック SHARE UPDATE EXCLUSIVE（読み書きと並行して実行できる） ACCESS EXCLUSIVE（SELECT も含めて全操作が止まる）
必要な空き容量 ほぼ不要 テーブルのコピーを作る分の空き容量が必要
時間 短い 長い
実行頻度 日常的に（autovacuum が自動で行う） 極端に肥大化したときだけ
  • ⚠ VACUUM FULL はテーブルを排他ロックする。運用中に実行すると業務が止まる
  • ⚠ autovacuum は VACUUM FULL を実行しない

書き方

VACUUM;                         -- 現在のデータベースの全テーブル
VACUUM emp;                     -- テーブルを指定
VACUUM FULL emp;
VACUUM ANALYZE emp;             -- VACUUM の後に ANALYZE
VACUUM VERBOSE emp;             -- 処理の詳細を表示
VACUUM FREEZE emp;              -- 行を積極的に凍結
VACUUM (FULL, VERBOSE, ANALYZE) emp;   -- 括弧でまとめて指定
  • ⚠ VACUUM はトランザクションブロック内で実行できない（→ 04章）
  • テーブルの所有者・DB の所有者・スーパーユーザーが実行できる（権限のないテーブルは警告を出して飛ばす）
  • OS のコマンドからは vacuumdb（→ 05章）

トランザクション ID の周回

  • トランザクション ID（XID）は 32ビット（約42億）で、使い切ると一周する。行の新旧を比べられるのは前後約 20億まで
  • 古い行を 凍結（FREEZE） して「どのトランザクションから見ても過去」の印を付けないと、古いデータが見えなくなる（データ消失に見える）
  • そのため、autovacuum を off にしていても、周回が近づくと周回防止のための autovacuum が強制的に実行される（autovacuum_freeze_max_age、デフォルト 2億トランザクション）

2. ANALYZE ★★★

ANALYZE;              -- 現在のデータベースの全テーブル
ANALYZE emp;
ANALYZE emp (name);   -- 列を指定
ANALYZE VERBOSE emp;
  • テーブルの統計情報（行数、列の値の分布、NULL の割合など）を集め、システムカタログ pg_statistic に保存する（見やすい形のビューは pg_stats）
  • 統計情報はプランナ（実行計画を立てる部分）が使う。古いと遅い実行計画が選ばれる
  • テーブル全体ではなくサンプリングした行を読む（大きいテーブルでも速い）
  • ロックは SHARE UPDATE EXCLUSIVE（読み書きと並行できる）
  • ⚠ ANALYZE はトランザクションブロック内でも実行できる（VACUUM はできない）
  • 大量のデータを入れた後（COPY、大きな INSERT）は ANALYZE を実行すると良い

3. autovacuum（自動バキューム） ★★★

  • autovacuum ランチャーが定期的に起動し、autovacuum ワーカーが必要なテーブルに VACUUM と ANALYZE を自動実行する
  • デフォルトで有効（autovacuum = on）
パラメータ デフォルト 意味
autovacuum on autovacuum を使う（sighup）
track_counts on テーブルの更新件数などの統計を集める。⚠ off にすると autovacuum が動かない
autovacuum_naptime 1min 各データベースをチェックする間隔
autovacuum_max_workers 3 同時に動くワーカーの最大数（postmaster）
autovacuum_vacuum_threshold 50 VACUUM するための最小の不要タプル数
autovacuum_vacuum_scale_factor 0.2 テーブルの行数に対する割合（20%）
autovacuum_analyze_threshold 50 ANALYZE するための最小の変更行数
autovacuum_analyze_scale_factor 0.1 テーブルの行数に対する割合（10%）
autovacuum_freeze_max_age 2億 周回防止の VACUUM を強制する XID の年齢
log_autovacuum_min_duration -1（無効） 指定時間以上かかった autovacuum をログに出す
  • VACUUM が実行される条件: 不要タプル数 > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × 行数
    • 例: 1万行のテーブル → 50 + 0.2 × 10000 = 2,050行を超えると VACUUM
  • ANALYZE も同様（50 + 0.1 × 行数 を超える変更）
  • テーブルごとに変えられる: ALTER TABLE emp SET (autovacuum_vacuum_scale_factor = 0.05);、ALTER TABLE emp SET (autovacuum_enabled = false);
  • 実行状況は pg_stat_user_tables で確認: n_live_tup（有効な行数）、n_dead_tup（不要タプル数）、last_vacuum / last_autovacuum、last_analyze / last_autoanalyze

5. ロール（ユーザー）の管理 ★★★

ロールとは

  • PostgreSQL ではユーザーとグループを区別せず「ロール」として扱う
  • ログインできるロール = ユーザー、他のロールをメンバーにまとめるロール = グループ
  • ⚠ ロールはクラスタ全体で共通（データベースごとではない）。pg_dump では出力されない（→ 07章）

CREATE ROLE / CREATE USER

CREATE ROLE alice LOGIN PASSWORD 'secret';
CREATE USER bob PASSWORD 'secret' CREATEDB VALID UNTIL '2027-03-31';
CREATE ROLE staff;                    -- グループ用（ログイン不可）
  • ⚠ CREATE USER は LOGIN 付きの CREATE ROLE。CREATE ROLE のデフォルトは NOLOGIN（ログインできない）
属性 意味 デフォルト
SUPERUSER / NOSUPERUSER すべての権限チェックを飛ばす NOSUPERUSER
CREATEDB / NOCREATEDB データベースを作れる NOCREATEDB
CREATEROLE / NOCREATEROLE ロールを作成・変更・削除できる NOCREATEROLE
LOGIN / NOLOGIN ログインできる CREATE ROLE は NOLOGIN、CREATE USER は LOGIN
REPLICATION / NOREPLICATION レプリケーション接続・pg_basebackup ができる NOREPLICATION
INHERIT / NOINHERIT メンバーになっているロールの権限を自動で引き継ぐ INHERIT
BYPASSRLS 行単位セキュリティを無視する NOBYPASSRLS
PASSWORD '...' パスワード なし
VALID UNTIL '日時' パスワードの有効期限 無期限
CONNECTION LIMIT n 同時接続数の上限 -1（無制限）
  • ⚠ VALID UNTIL はパスワードの期限（ロール自体が消えるわけではない。peer 認証などでは影響しない）

ALTER ROLE / DROP ROLE

ALTER ROLE alice CREATEDB;
ALTER ROLE alice PASSWORD 'newpass';
ALTER ROLE alice RENAME TO alice2;     -- MD5 パスワードは名前を含むので消える
ALTER ROLE alice SET work_mem = '16MB';  -- 接続時のパラメータ（→ 06章）
DROP ROLE alice;
DROP ROLE IF EXISTS alice;
  • ⚠ オブジェクトを所有している、または権限を与えられているロールは DROP ROLE できない（エラー）。先に次を実行する
    • REASSIGN OWNED BY alice TO bob;: alice が所有するオブジェクトの所有者を bob に変える
    • DROP OWNED BY alice;: alice が所有するオブジェクトを削除し、alice に与えた権限も取り消す
    • ⚠ どちらも今のデータベースの中だけが対象。他のデータベースでも実行する必要がある

ロールのメンバーシップ（グループ）

GRANT staff TO alice;          -- alice を staff のメンバーにする
REVOKE staff FROM alice;
SET ROLE staff;                -- staff として振る舞う（RESET ROLE で戻る）
  • INHERIT（デフォルト）なら、alice は何もしなくても staff の権限を使える。NOINHERIT なら SET ROLE が必要
  • ⚠ SUPERUSER・CREATEDB などの属性はメンバーシップで継承されない（権限だけが継承される）。使うには SET ROLE が必要

定義済みロール

ロール 内容
pg_read_all_data すべてのテーブルを読める（14〜）
pg_write_all_data すべてのテーブルに書ける（14〜）
pg_read_all_settings / pg_read_all_stats 全設定 / 全統計情報を見られる
pg_monitor 監視用（上の2つなどを含む）
pg_read_server_files / pg_write_server_files サーバのファイルを COPY で読める / 書ける
pg_signal_backend 他のセッションのキャンセル・終了ができる

6. 権限（GRANT / REVOKE） ★★★

基本

  • オブジェクトを作ったロールが所有者になり、所有者はすべての権限を持つ（ALTER・DROP できるのは所有者とスーパーユーザーだけ）
  • 他のロールは、GRANT で権限を与えられないと使えない
  • スーパーユーザーは権限チェックを受けない
GRANT SELECT, INSERT ON emp TO alice;
GRANT ALL PRIVILEGES ON emp TO alice;       -- PRIVILEGES は省略可
GRANT SELECT ON ALL TABLES IN SCHEMA app TO alice;  -- スキーマ内の既存の全テーブル
GRANT SELECT (id, name) ON emp TO bob;      -- 列単位
GRANT UPDATE (salary) ON emp TO bob;
GRANT SELECT ON emp TO PUBLIC;              -- 全ロール
GRANT SELECT ON emp TO alice WITH GRANT OPTION;  -- alice も他人に与えられる
REVOKE INSERT ON emp FROM alice;
REVOKE ALL ON emp FROM PUBLIC;
REVOKE GRANT OPTION FOR SELECT ON emp FROM alice;  -- 再付与の権利だけ取り消す
ALTER TABLE emp OWNER TO bob;               -- 所有者の変更
  • PUBLIC: すべてのロール（今後作られるロールも含む）を表す特別な名前
  • ⚠ WITH GRANT OPTION で受け取った権限を他人に与えていた場合、元の権限を REVOKE するには CASCADE が必要（付けないとエラー）
  • ⚠ PUBLIC から REVOKE しても、個別に GRANT された権限は残る
  • ⚠ ON ALL TABLES IN SCHEMA は今あるテーブルだけ。今後作るテーブルにも与えるには ALTER DEFAULT PRIVILEGES
  • 確認: psql の \dp / \z（例: alice=arw/postgres = postgres が alice に a・r・w を与えた）

主な権限

対象 権限
テーブル SELECT（r）、INSERT（a）、UPDATE（w）、DELETE（d）、TRUNCATE（D）、REFERENCES（x。外部キーで参照する）、TRIGGER（t）
列 SELECT、INSERT、UPDATE、REFERENCES
シーケンス USAGE（nextval・currval）、SELECT（currval）、UPDATE（nextval・setval）
データベース CONNECT（接続）、CREATE（スキーマを作る）、TEMPORARY（一時テーブルを作る）
スキーマ USAGE（中のオブジェクトにアクセス）、CREATE（中にオブジェクトを作る）
関数・プロシージャ EXECUTE
テーブルスペース CREATE
  • ⚠ テーブルの SELECT 権限があっても、そのスキーマの USAGE 権限がないとアクセスできない
  • ⚠ UPDATE・DELETE で WHERE を使うと、条件の列を読むため SELECT 権限も必要
  • ⚠ 外部キーを作るには、参照先テーブルの REFERENCES 権限が必要

PUBLIC にデフォルトで与えられている権限（14）

  • データベース: CONNECT、TEMPORARY
  • 関数: EXECUTE
  • public スキーマ: USAGE と CREATE（⚠ 15 で CREATE は外された。試験は 14 基準）
  • ⚠ テーブル・ビュー・シーケンスには何も与えられていない（所有者以外は GRANT が必要）
  • 特定のデータベースへの接続を制限するには REVOKE CONNECT ON DATABASE sampledb FROM PUBLIC; してから、必要なロールに GRANT CONNECT する（pg_hba.conf でも制限できる）

7. データベースの作成・削除 ★★★

CREATE DATABASE sampledb;
CREATE DATABASE sampledb
  OWNER alice
  TEMPLATE template0
  ENCODING 'UTF8'
  LC_COLLATE 'C'
  LC_CTYPE 'C'
  TABLESPACE fastspace
  CONNECTION LIMIT 50;
ALTER DATABASE sampledb RENAME TO sample2;
ALTER DATABASE sampledb OWNER TO bob;
DROP DATABASE sampledb;
DROP DATABASE IF EXISTS sampledb;
DROP DATABASE sampledb WITH (FORCE);   -- 接続中のセッションを切断して削除（13〜）
  • CREATE DATABASE は既存のデータベースを複製して作る。デフォルトの複製元は template1
    • template1 に入れたテーブルや拡張機能は、以後作るデータベースにも入る
    • template0 は initdb 直後の素の状態。template1 と違うエンコーディング・ロケールで作るときは template0 を指定する（template1 のままだとエラー）
  • 実行できるのは CREATEDB 属性を持つロールかスーパーユーザー
  • ⚠ 複製元のデータベースに他のセッションが接続していると CREATE DATABASE は失敗する
  • ⚠ DROP DATABASE は、そのデータベースに誰か接続していると失敗する（自分が接続中のデータベースも削除できない）。13 以降は WITH (FORCE) で切断して削除できる
  • ⚠ CREATE DATABASE / DROP DATABASE はトランザクションブロック内で実行できない
  • DROP DATABASE できるのは所有者とスーパーユーザー

8. テーブルスペース ★★★

  • データファイルを置くディレクトリに名前を付けたもの。容量が足りないとき、速いディスクに特定のテーブルを置きたいときに使う
CREATE TABLESPACE fastspace LOCATION '/ssd/pgdata';
CREATE TABLESPACE fastspace OWNER alice LOCATION '/ssd/pgdata';
CREATE TABLE logs (...) TABLESPACE fastspace;
CREATE INDEX ... ON logs (...) TABLESPACE fastspace;
ALTER TABLE logs SET TABLESPACE pg_default;   -- 移動（ACCESS EXCLUSIVE ロック）
SET default_tablespace = fastspace;           -- テーブルスペース省略時の作成先
DROP TABLESPACE fastspace;
  • ⚠ LOCATION は絶対パス。ディレクトリはあらかじめ存在し、空で、OS の postgres ユーザーが所有していること（作ってはくれない）
  • ⚠ CREATE TABLESPACE はスーパーユーザーだけが実行できる。トランザクションブロック内では実行できない
  • ⚠ 中にオブジェクトが残っているテーブルスペースは DROP できない（全データベースで空にする必要がある）
  • データディレクトリの pg_tblspc/ に、テーブルスペースの OID の名前でシンボリックリンクができる
  • 初めからある2つ
テーブルスペース 内容
pg_default データベースのデフォルト（template1・template0 の格納先）。実体は base/
pg_global クラスタ共通のシステムカタログ用。実体は global/
  • テーブルスペースはクラスタ全体で共通（pg_dump では出力されない → pg_dumpall）
  • 確認: psql の \db、システムカタログ pg_tablespace

9. システムカタログと情報スキーマ ★★★

システムカタログ

  • PostgreSQL が自分の管理情報（テーブル・列・ロールなどの定義）を入れているテーブル。pg_catalog スキーマにあり、名前は pg_ で始まる
  • search_path に書かなくても、pg_catalog は常に最初に検索される
カタログ / ビュー 内容
pg_database データベースの一覧（クラスタ共通）
pg_class テーブル・インデックス・シーケンス・ビューなど（リレーション）。relkind 列で種類を区別
pg_attribute テーブルの列
pg_namespace スキーマ
pg_index インデックスの詳細
pg_proc 関数・プロシージャ
pg_type データ型
pg_authid ロール（パスワードを含む。スーパーユーザーのみ読める）
pg_roles ロール（pg_authid のパスワードを伏せたビュー。誰でも読める）
pg_user LOGIN できるロールのビュー
pg_tablespace テーブルスペース
pg_tables / pg_indexes / pg_views テーブル / インデックス / ビューを見やすくしたビュー
pg_settings パラメータの現在値（→ 06章）
pg_statistic / pg_stats 統計情報（→ ANALYZE）
pg_locks 現在のロック（→ 04章）
  • pg_class の relkind: r = テーブル、i = インデックス、S = シーケンス、v = ビュー、m = マテリアライズドビュー、t = TOAST テーブル、f = 外部テーブル、p = パーティションテーブル、c = 複合型
  • 多くのオブジェクトは OID（オブジェクト識別子）で識別される。SELECT oid, datname FROM pg_database;

ビュー 内容

  • 統計をリセット: SELECT pg_stat_reset();（現在のデータベース）

情報スキーマ（information_schema）

  • SQL 標準で定められたビューの集まり。他の DBMS でも同じ問い合わせが使える（移植性が高い）

  • ⚠ PostgreSQL 独自の情報（インデックスなど）は含まない。それらはシステムカタログで見る

SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'emp';
